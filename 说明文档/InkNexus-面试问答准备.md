## 一、句 1：微服务拆分、Nacos、网关鉴权

> 简历原句：按业务域拆分 6 个微服务、网关及 AI 客服服务，使用 Nacos 统一服务注册与配置；Gateway 统一 JWT 鉴权并透传用户身份，下游服务校验资源归属，防止水平越权。

**面试官会盯的钩子**：拆分依据、"透传"怎么防伪造、"水平越权"具体怎么防、JWT 的固有缺陷。

### Q1.1 为什么拆成这几个服务？拆分依据是什么？会不会拆得太细？

**参考回答**：我按业务域和能力变化频率拆的：auth 是身份域、book 是商品目录域、cart 是交易前置域、stock 是库存域、order 是交易域、payment 是支付域。拆的原则是**每个服务有独立的领域模型和独立的数据表**，比如库存单独拆出来，是因为它的读写模式和订单完全不同——库存是热点单行更新，需要独立的连接池和优化空间，和订单的长事务混在一起会互相拖累。拆完后服务间只有两种依赖方向：交易链路 order 依赖 book/cart/stock，事件链路走 MQ，没有循环依赖。

坦率说，这个项目的流量撑不起六个服务，拆分也包含架构演练的目的。如果是生产上的小系统，我会倾向先做**模块化单体**（modulith），按同样的包边界组织，等某个域的扩展需求真出现了再物理拆分——拆分的成本不在开发期而在运维期，链路追踪、分布式事务、部署编排都是代价。

### Q1.2 服务之间怎么通信？为什么用 Feign 同步调用？同步链路上某个服务挂了怎么办？

**参考回答**：两种方式并存，按语义选型。**命令类的、需要即时结果的走 Feign 同步**：下单时 order 调 book 拿价格快照、调 stock 预占库存、调 cart 拉取勾选商品。**状态通知类的走 RabbitMQ 异步事件**：支付成功、库存确认/释放、延迟关单，这些不需要同步返回值，而且要求"上游成功后下游最终必须执行"，天然适合事件驱动。

同步链路失败的处理原则是：**下单是"全成功或全失败"的**——book 挂了拿不到价格快照就直接失败，用户重试；stock 预占失败就整单失败。这里有一个关键设计：Feign 预占库存是**远程操作、本地事务回滚不了它**，所以我把预占放在落库之前，本地落库一旦失败就走补偿链路 `releaseStockQuietly` 发库存释放事件，把远程已扣的库存还回去。

另外我做过一个优化：购物车下单要拿多本书的价格，最初是一本一本调 book 服务（N+1 次 Feign 调用），后来改成 `GET /books/by-ids` 一条 IN 批量接口，一次调用拿全。单测里有专门一个回归用例守住这个优化（`createOrderFromCart_batchFetchesBooks_andCreatesOrder`，verify 永远不走单本查询）。

### Q1.3 Nacos 在项目里起了什么作用？了解它的原理吗？AP 还是 CP？

**参考回答**：两个作用：服务注册发现 + 统一配置管理。配置上我把 DB、Redis、JWT 密钥、RabbitMQ 可靠性参数全部放在 Nacos 的 per-service yaml 里（auth.yaml、order.yaml 等），本地 application.yml 只留端口和 Nacos 地址，用 `spring.config.import: optional:nacos:xxx.yaml` 导入，有一键发布脚本。

原理层面：Nacos 客户端每 5 秒向注册中心发心跳，不健康实例 15 秒标记、30 秒剔除；服务发现走客户端本地缓存 + 订阅推送。AP/CP 的问题要分场景答：**临时实例（默认，心跳模式）走 Distro 协议是 AP**，可用性优先、允许短暂不一致；**持久化实例走 Raft 是 CP**。我服务全是临时实例，注册发现场景选 AP 是对的——注册中心短暂的数据不一致可以容忍，但不可用会导致整个调用链瘫痪。配置中心这块，Nacos 客户端长轮询（30 秒周期）感知配置变更，配合 `@RefreshScope` 或配置绑定类热刷新，我改 expire-minutes 这类参数不用重启服务（但 MQ 队列的 TTL 参数是声明时固定的，改了要删队列重建——这是另一个问题了，MQ 那边可以展开）。

### Q1.4 为什么把 JWT 鉴权放在网关统一做？而不是每个服务自己校验？

**参考回答**：一是收敛信任边界：验签密钥只存在于网关，下游服务根本拿不到 JWT，也不需要引入 JWT 依赖，它们只信任网关写入的 `X-User-Id` 头；二是职责分离，网关管"你是谁"，服务管"你能不能动这条资源"；三是策略统一，白名单、公开只读路径（GET /api/books、GET /api/stock）这些规则只维护一处。代价是网关成为单点，所以我用 Nacos 的 `lb://` 负载均衡可以多实例部署网关；另外服务内部调用（Feign）不经过网关，这个信任模型要清楚——**服务间内网通信不在网关鉴权范围内**，生产上要配 mTLS 或网络隔离兜底，这是我明确知道的边界。

### Q1.5 关键问题：客户端自己伪造一个 X-User-Id 头，怎么防？

**参考回答**：两层防线。第一层在网关：构建转发请求时用 `request.mutate().header(...)`，这个方法是 **put 覆盖语义**，不管客户端带没带 `X-User-Id` / `X-User-Role`，都会被 JWT 解析结果整体替换，伪造头活不到下游。第二层在下游的编码纪律：所有 Controller 一律 `@RequestHeader("X-User-Id")` 从头取身份，**从不接收请求体里的 userId 字段**。这个点我有单测：`AuthGlobalFilterTest.filter_overridesForgedUserIdHeader_whenClientSuppliesOne`，专门模拟客户端带伪造头然后断言被覆盖。

还有一个细节可以主动讲：旧版签发的 token 里没有 role claim，网关对这种 token 统一按 `USER` 透传——管理接口对存量 token 默认拒绝，**fail-closed**，宁可误伤也不放行。

### Q1.6 下游服务怎么校验资源归属、防水平越权？举个真实例子。

**参考回答**：原则是"**查询和写入都带 userId 条件**"，不给"先查出来再判断"以外的信任。举两个真实例子：查订单详情时 `getOrderDetail(id, userId)` 查到订单后比对 `order.getUserId()`，不是本人的**返回 null，Controller 统一回 404 "订单不存在"**——注意是 404 不是 403，不向攻击者泄露"这个订单存在但不是你的"这个信息。地址服务更直接：`getOwnedAddress` 用 `id + userId` 联合条件查询，别人的 addressId 在你这里查出来就是 null，update/delete/setDefault 全部先过这个方法。购物车所有接口同样只认 header 里的 userId。

AI 服务这条链也做了：网关注入的 `X-User-Id` 被 `UserContextInterceptor` 存进 ThreadLocal（`afterCompletion` 里 clear 防线程复用串号），Feign 拦截器调下游时把它写回 `X-User-Id` 头，订单服务照常校验归属——所以 AI 查订单走的权限链路和用户直接查完全一样。

### Q1.7 JWT 是无状态的，那登出和 token 吊销怎么办？（⚠️ 诚实回答点）

**参考回答**：先坦白：当前版本没有做登出和黑名单，token 有效期 24 小时，纯无状态验签。这是我明确知道的设计缺口。如果要做，方案我有预案：**短 access token（比如 15 分钟）+ refresh token**，refresh token 存 Redis 可吊销；或者网关加 Redis 黑名单，登出时把 jti 写进去，网关验签后多查一次黑名单——代价是网关每请求多一次 Redis 查询，把"无状态"退化成"有状态"，所以做不做要看业务对吊销时效的要求。我目前这个项目对外卖的场景，24 小时内的 token 残留风险可以接受，但如果接了支付真实资金，这个必须补。

### Q1.8 TraceId 链路是怎么做的？

**参考回答**：网关有个 `TraceIdGlobalFilter`（order -200，先于鉴权 -100 执行）：请求头里已有 `X-Trace-Id` 就透传，没有就生成 32 位 UUID，并回写到响应头——联调报障时用户给一个编号就能定位。下游每个服务通过 common 包里的 `TraceIdFilter`（`OncePerRequestFilter`，最高优先级）把这个头写进 SLF4J 的 MDC，日志 pattern 里配了 `%X{traceId}`，所以一次请求跨 6 个服务的所有日志行都带同一个 traceId，一条 `grep` 就能串起完整调用链。请求结束在 finally 里 `MDC.remove()`，防线程复用串号。Feign 调用时也有拦截器把 traceId 继续往下传。

## 二、句 2：订单-支付-库存闭环（防超卖 + 多层幂等 + 补偿）

> 简历原句：设计订单-支付-库存业务闭环，通过条件原子更新与库存状态控制避免超卖；结合下单唯一索引、支付状态条件更新、消费端 eventId 去重实现多层幂等，并对异常场景补偿释放预占库存。

**面试官会盯的钩子**：条件原子更新长什么样、为什么不用分布式锁/Redis、每一层幂等防的是哪个场景、补偿链路全不全。

### Q2.1 具体讲讲怎么防超卖的？

**参考回答**：核心是**两段式库存模型 + 条件原子更新**。库存表 `t_book_stock` 有两个字段：`stock`（可售）和 `locked_stock`（预占）。下单预占的 SQL 是这样的：

```sql
UPDATE t_book_stock
SET stock = stock - #{quantity},
    locked_stock = locked_stock + #{quantity},
    version = version + 1
WHERE book_id = #{bookId} AND stock >= #{quantity}
```

防超卖就靠两点：第一，`stock - n` 和 `WHERE stock >= n` 在同一条 UPDATE 里，MySQL 对单行 UPDATE 持行锁、语句本身原子，并发扣减不可能把 stock 扣成负数；第二，用**受影响行数**做裁决——更新返回 0 行说明库存不足，直接抛 `BusinessException(400, 库存不足)`，一次预占一批商品是在同一个 `@Transactional` 里，任何一本不足**整批回滚**，不会出现"扣了 A 没扣到 B"的半程状态。

支付成功后 `confirmStock` 只减 `locked_stock`（`WHERE locked_stock >= n`），因为可售库存在下单那一刻已经真实扣掉了；取消或超时则 `releaseStock` 把库存加回。这样"可卖多少"始终只由 stock 决定，预占和确认不会重复扣减。

### Q2.2 为什么用数据库条件更新，而不是分布式锁或 Redis 预扣？

**参考回答**：三者我对比过。**分布式锁（SETNX）**解决的是"串行化临界区"，但我的临界区只有一条 UPDATE——数据库行锁本身就已经把它串行化了，再加一层 Redis 锁是同义反复，还引入锁过期、续期、死锁这些新故障面。**Redis 预扣**（DECR + 判断负数回滚）是秒杀级热点单品的方案，它的代价是要解决 Redis 和 DB 的最终一致（异步落库、对账、Redis 宕机恢复），复杂度高一个量级。我的场景是常规电商下单，瓶颈不在这一行 UPDATE，数据库条件更新的吞吐完全够，**用最低复杂度满足正确性**是我选型的第一原则。我留的演进路径也很清楚：如果出现单 SKU 秒杀级热点，第一优先把该 SKU 改为 Redis 预扣 + MQ 异步落库，或者做库存分段。

### Q2.3 表里还有个 version 字段，做什么用的？

**参考回答**：诚实地说，防超卖的正确性由 `WHERE stock >= n` 保证，不依赖 version；version 是我预留的乐观锁字段（MyBatis-Plus 乐观锁插件的标准字段），每次库存变更 +1。当前代码里它起到的是**变更计数器**的作用，排障时能看出某行被改过多少次。我没有启用乐观锁重试，因为单行条件更新已经原子了，重试反而画蛇添足。面试官如果追问"既然不用为什么留着"——答案是表结构为演进留了余量，真到需要 CAS 多字段语义时不用改表。

### Q2.4 下单幂等怎么做的？唯一索引建在哪、防的是什么场景？

**参考回答**：防的是**前端重复提交**：用户双击下单按钮、网络超时后重发、页面回退再提交。方案是前端在**打开下单弹窗时生成一个 `clientRequestId`**（不是点按钮时生成——这样同一次购买意图无论点多少次按钮都是同一个请求号），后端 `t_order` 表建了联合唯一索引 `uk_user_request (user_id, client_request_id)`。带 user_id 是因为请求号只在用户维度需要唯一，避免跨用户碰撞，也防止恶意用别人的请求号。

插入命中唯一索引时 Spring 翻译成 `DuplicateKeyException`，我的处理不是报错，而是**幂等命中**：先把本次重复预占的库存补偿释放掉，再按 `userId + client_request_id` 查出**已有那笔订单返回给用户**——用户看到的是同一笔订单，无任何新增副作用。这里有个分支要注意：如果查不到已有订单（说明冲突不是幂等键造成的，比如订单号真撞了），就把原始异常抛出去，不能吞。单测 `createOrder_returnsExistingOrder_whenDuplicateRequestId` 覆盖了完整行为：返回旧订单、verify 释放事件发了、verify 关单延迟消息**没有**发。

补充一个细节：`client_request_id` 允许 NULL，MySQL 唯一索引对多个 NULL 不拦截，所以不带请求号的调用（比如压测以外的内部调用）不受幂等约束，这是故意留的口子。压测脚本里每个请求用 `${__UUID}` 独立请求号，正好走真实幂等链路。

### Q2.5 支付怎么幂等？用户连点两次支付按钮会怎样？

**参考回答**：三层。第一层，`t_payment` 表 `order_id` 唯一索引——一单最多一笔支付单，并发双击两个事务同时 insert，必有一个撞唯一键回滚。第二层，重复请求先查：已存在且 `status=1` 的支付单**直接返回，不再发布 PaySuccess 事件**——这点很关键，重发事件会导致订单侧对同一订单二次确认库存、错误扣减其他订单的锁定库存。第三层，金额不信任前端：支付金额以 order 服务返回的订单总额为准。另外支付前有状态校验（`getPayableOrder`）：订单已取消/已完成、已过期的都不能发起支付，校验还包含归属校验（403）。单测里对应 `pay_publishesPaySuccessOnlyOnce_whenSameOrderPaidTwice`。

### Q2.6 消息重复消费的根本原因是什么？eventId 去重具体怎么实现的？

**参考回答**：先说根因：RabbitMQ 的投递语义是 at-least-once——消费端处理完还没发 ACK 就宕机，Broker 会重投；网络抖动导致 ACK 丢失也重投。所以**消费端必须按幂等设计**，去重不是可选优化。

实现上，每个事件在发布时就生成 UUID 作为 `eventId`（重投不变），stock 侧消费时第一件事是往 `t_mq_consumed_log` 表执行：

```sql
INSERT IGNORE INTO t_mq_consumed_log (message_id, consumer) VALUES (#{messageId}, #{consumer})
```

表上 `message_id` 唯一索引。这里有两个设计点我比较得意：**第一，用 INSERT IGNORE 的返回值判定而不是先 SELECT 再 INSERT**——先查后插在并发重投下有竞态（两个消费者同时查都说不存在），INSERT IGNORE 把判重和占位合成一个原子操作，返回 0 就是消费过。**第二，去重插入和库存更新在同一个 `@Transactional` 里**：去重记录插成功但后续库存 UPDATE 抛异常，整个事务回滚、去重记录一起消失，消息重投后还能正常重试——不会出现"去重表记了、业务没做成"的死局。反过来业务成功后记录保留，重投的插不进去，返回 0 直接跳过。

还有个兜底：万一 eventId 缺失（空字符串），`markConsumed` 按首次消费处理，幂等退化为业务层保证——释放 SQL 里的 `LEAST(locked_stock, n)` 钳制和订单状态条件更新仍然兜得住。单测覆盖了"已消费跳过（verifyNoInteractions 到 stockMapper）"、"eventId 缺失照常执行"、"JSON 毒消息直接丢弃不重投"这些分支。

### Q2.7 预占的库存什么时候释放？补偿有哪些触发点？

**参考回答**：释放的触发点有四个，全部收敛到同一条链路——发 `order.stock.release` 事件，stock 消费后执行带 `LEAST` 钳制的释放 SQL：**① 下单落库失败**（任何异常，包括幂等命中后的重复预占）；**② 用户主动取消**（订单 0→2 成功后同事务发事件）；**③ 超时关单**（延迟消息消费成功后发）；**④ 兜底扫描关单**（和 ③ 复用同一个 `closeExpiredOrder`）。值得强调的是发布失败的处理：取消和关单链路里发释放事件失败会**抛异常回滚订单状态变更**，让订单停留在待支付，下一轮重试——宁可晚释放，不能让库存泄漏。

有个要坦白的边界：因为支付是 mock 的，"支付失败释放"这个场景实际不存在（mock 永远成功，`t_payment` 的失败状态字段预留未用）；同样**没有退款逻辑**。接入真实支付渠道时，支付失败回调、退款单这些要在这个骨架上加，释放/确认的事件链路是可以复用的。

### Q2.8 订单状态机是怎么设计的？全部状态流转怎么保证正确？

**参考回答**：`t_order.status`：0 待支付、1 已支付、2 已取消、3 已完成。四条流转边**全部用条件更新驱动**，不接受无条件 set：

- **0→1**（`markPaid`）：唯一入口是 MQ 消费者 `PaySuccessConsumer`，**刻意不提供 HTTP 接口**，防止绕过支付直接改单。`UPDATE ... WHERE status=0`，更新成功才在同一事务里发库存确认事件；更新 0 行时查一下现状——已是 1 视为幂等成功，是 2（已取消）就打 warn 后正常 ACK，**不发确认事件**，库存随后由关单链路释放。
- **0→2**（取消 / 超时关单）：条件里分别带 userId 和 `expire_time <= now`。
- **1→3**（确认收货）：`WHERE status=1`，已是 3 幂等成功。

这里有个我踩过的真实坑值得讲：**幂等命中时绝不能重发确认事件**。重复的 PaySuccess 消息到达时订单已经是 1，如果图省事再发一次 `order.paid`，stock 那边 `confirmStock` 会再去减 `locked_stock`——减的就是**其他订单**的预占库存，等于把别人的库存确认掉了。所以规则是：**确认事件只在状态真正迁移（0→1）的那一刻发布一次**。对应的单测是 `markPaid_publishesConfirmOnlyOnce_whenPaySuccessMessageRedelivered`，用 `thenReturn(1, 0)` 模拟同一消息消费两次，verify 发布恰好一次。

### Q2.9 超时关单和支付成功并发（用户在最后一秒付款）怎么办？

**参考回答**：两道防线。第一道，**支付入口前置校验**：发起支付时订单已过期（`expireTime < now`）直接拒绝"订单已超时，请重新下单"，不依赖关单任务是否已经跑。第二道，**状态条件更新仲裁竞态**：就算校验通过后、`markPaid` 执行前订单恰好被关单线程置成 2，`UPDATE WHERE status=0` 影响 0 行，走"已取消"分支，支付消息被 warn + ACK 丢弃，**库存确认事件不会发**——预占库存留给关单链路释放，账目不乱。反方向同理：关单的 `WHERE status=0 AND expire_time<=now` 在订单已支付时必然 0 行，关不掉已付订单。

要坦白的残余缺口：极端情况下"支付单已落库成功、PaySuccess 已发出，但订单恰好在窗口内被关"，会留下支付单已付、订单已取消的不一致——**当前没有自动退款补偿**，靠"过期订单不可支付"的前置校验把窗口压到秒级。生产化做法是加一个对账任务扫"支付成功但订单非已支付"的记录走退款，这是我清楚的改进项。

### Q2.10 为什么不用 Seata 做分布式事务？

**参考回答**：我的场景里跨服务写操作只有"下单预占库存"这一处，且业务上允许**最终一致**——用户可以容忍下单失败重试，不能容忍的是超卖和库存泄漏，而这两点已经被条件更新 + 补偿释放解决了。Seata AT 模式的代价是：全局锁让热点行（同一本书的库存行）的并发吞吐下降、每个参与者要落 undo_log、TC 集群要维护——这些成本换来的强一致我并不需要。我的方案本质是手写的 Saga：正向操作（预占）+ 补偿操作（释放），每一步幂等，靠事件驱动推进。如果未来出现"必须同成败"的跨服务写（比如下单同时扣优惠券和库存且不可补偿），我会局部引入 Seata TCC 而不是全局 AT。

## 三、句 3：RabbitMQ 延迟关单与消息可靠性

> 简历原句：基于 RabbitMQ TTL + 死信实现订单延迟关单，并结合定时扫描兜底；生产端使用 Publisher Confirm、消费端失败重试与死信处理，保障订单与库存状态最终一致。

**面试官会盯的钩子**：为什么不用延迟插件、队头阻塞、兜底和主链路的并发仲裁、confirm 之后消息丢了怎么办。

### Q3.1 延迟关单的整体方案？为什么用 TTL+死信，不用延迟插件、定时轮询或 Redis zset？

**参考回答**：拓扑是：下单成功后发一条消息到 `inknexus.order.close.delay.queue`，这个队列声明了 `x-message-ttl = 30分钟`、`x-dead-letter-exchange = inknexus.order.close.exchange`；消息到期后死信投递到绑定的 `inknexus.order.close.queue`，消费者执行 `closeExpiredOrder` 条件关单。选型对比：

- **定时轮询**（每分钟扫全表待支付订单）：实现最简单，但延迟精度差、空扫浪费，订单量大时对 DB 是持续压力。我把它降级为**兜底**而不是主链路。
- **Redis zset**（score 存到期时间，轮询 zrangebyscore）：引入新的存储，Redis 和订单库之间又多一层一致性要维护。
- **RabbitMQ 延迟插件**：能力最好（任意延迟级别），但要给 Broker 装插件，运维上多一个依赖；而且我的延迟值是**统一的 30 分钟**，原生 TTL 就够。
- **TTL+死信是原生能力、零插件**，代价是队列参数固定。这里有个关键决策：我用的是**队列级 TTL 而不是消息级 TTL**——如果同一队列里消息各带 TTL，RabbitMQ 只检查队头，前面一条 10 分钟的消息会阻塞后面 1 分钟到期的消息（head-of-line blocking）。我的过期时间全局统一，队列级 TTL 天然规避这个问题，这个坑是我在设计时明确绕开的，代码注释里写了。

另外一个运维细节也写在注释里：RabbitMQ 队列参数一经声明不可更改，调整 `expire-minutes` 后要删旧队列让它以新 TTL 重建——TTL 是从 Nacos 配置 `inknexus.order.expire-minutes` 读的，声明 Bean 时注入。

### Q3.2 定时扫描兜底怎么做的？和延迟消息同时触发，会不会重复关单、重复释放库存？

**参考回答**：兜底任务是 `OrderTimeoutTask`，cron 每 2 分钟，扫 `status=0 AND expire_time <= now` 的订单按过期时间升序、每批 500 条，逐单调同一个 `closeExpiredOrder`。单条失败 catch 住继续下一条，等下一轮再试——保持"库存和订单状态不变、下轮重试"的语义。

**防重复不靠分布式锁，靠数据库条件更新的原子性**：`closeExpiredOrder` 是 `UPDATE t_order SET status=2 WHERE id=? AND status=0 AND expire_time<=now`。延迟消息消费者和定时任务同时到达同一条订单，谁先把 0→2 更新成功谁生效，后到的拿到 0 行直接返回 false——**只有真正完成状态迁移的那一方才会往下走发库存释放事件**，所以不会重复关单，更不会重复释放。这和主链路的设计一脉相承：状态机的每次迁移本身就是互斥点。

兜底为什么必要：延迟消息的发送在下单链路里是**尽力而为**（发送失败只 warn 不阻断下单，否则消息故障会拖垮交易主流程），漏掉的订单全靠扫描补上；另外 RabbitMQ 不可用期间的所有超时订单也由它兜底。

### Q3.3 Publisher Confirm 具体做了什么？confirm 返回 nack 之后消息怎么办？

**参考回答**：配置是 `publisher-confirm-type: correlated` + `publisher-returns: true` + `template.mandatory: true`，通过 `RabbitTemplateCustomizer` 给 RabbitTemplate 挂两个回调：confirm 回调在 Broker 收不到/落盘失败时打 error 日志，`CorrelationData` 里放的是事件 eventId，日志能定位到具体订单；returns 回调捕获"到达 Broker 但路由不到任何队列"的消息，把 exchange、routingKey、消息体都记下来。

要诚实回答"nack 之后怎么办"：**当前只留证据、不自动重发**。这不是疏忽而是取舍——完整的可靠投递需要本地消息表（outbox）：业务和消息记录同事务落库、后台任务扫未确认记录重发、消费端幂等兜住重复。我的代码注释里明确写了这个判断：当前消息量和"兜底机制"（关单扫描、订单状态条件更新、人工查 DLQ）覆盖下，引入 outbox 的复杂度不划算；如果消息可靠性要求升级，outbox 是标准答案，而且我的 eventId 去重表已经为它铺好了消费端基础。

### Q3.4 消费端怎么保证消息不丢？重试策略是什么？重试耗尽后去哪？

**参考回答**：分四层。**第一层 ack 机制**：监听容器是默认 AUTO 模式，方法正常返回才 ACK，抛异常就 Nack——业务没做成消息就不算消费掉。**第二层本地重试**：`spring.rabbitmq.listener.simple.retry`，最多 3 次、初始间隔 1 秒、指数翻倍上限 10 秒，覆盖瞬时故障（DB 抖动、连接闪断）。**第三层死信**：`default-requeue-rejected: false`——重试耗尽后**不重回队列**（重回会立即再消费、变成无限快速循环），而是走每个业务队列声明时挂的 `x-dead-letter-exchange = inknexus.dlx.exchange`，用各自的 routing key（`dlx.pay.success`、`dlx.order.paid` 等）统一落进 `inknexus.dlx.queue` 等人工介入。**第四层兜底**：即使消息彻底丢了，业务上还有关单扫描、状态条件更新这些数据库侧的兜底，最终一致不依赖单条消息。

毒消息的处理也讲一下：JSON 解析失败的消息重试也没用（不是瞬时故障），直接丢弃不重投，避免死循环占满重试预算；真正的业务异常才走重试→死信。

### Q3.5 消息持久化怎么做的？

**参考回答**：三件套齐了：交换机、队列全部 durable 声明；Spring AMQP 的 RabbitTemplate 默认就是 PERSISTENT 投递（不需要显式设置 delivery mode）；Broker 侧队列落盘。这样 Broker 重启消息不丢。可以补一句认知：持久化消息也有落盘窗口（异步刷盘时宕机可能丢少量），镜像/仲裁队列（quorum queue）才是 Broker 高可用方案，单机部署下持久化解决的是"重启不丢"。

### Q3.6 本地事务和发消息不是原子的，怎么避免"订单改了消息没发出去"或反过来？

**参考回答**：我的模式是"**事务内发布、发布失败即回滚**"：`markPaid`、`cancelOrder`、`closeExpiredOrder` 里，状态条件更新成功后**在同一个事务方法里**发事件，发布抛异常会让整个事务回滚、订单状态回到迁移前，消息重投或兜底扫描让这单再来一次——所以"状态变了但事件丢了"被阻止了。反方向"事件发了但事务回滚"（发成功后 commit 失败）存在极小窗口：消费者会拿到一个订单状态还是 0 的 PaySuccess——但消费端是条件更新，0 行走"状态不可更新"分支，不会发库存确认，**消费端的幂等设计正好也消化了生产端的这个窗口**。两边合起来，最终一致成立。要做到严格不丢不重就是 outbox 方案，理由同 Q3.3。

### Q3.7 讲一下整个消息拓扑？有哪些交换机和队列？

**参考回答**：拓扑常量统一收敛在 common 的 `InkNexusRabbitMq` 类里，避免字符串散落对不上。共 5 个交换机 7 类队列：`inknexus.pay.success.exchange`（Topic）→ `inknexus.order.pay.success.queue`（payment 发、order 消费）；`inknexus.order.stock.exchange`（Topic）路由 `order.paid` 到库存确认队列、`order.stock.release` 到库存释放队列（order 发、stock 消费）；延迟关单链路 `inknexus.order.close.delay.queue`（TTL 30 分钟）→ 死信到 `inknexus.order.close.exchange`（Direct）→ `inknexus.order.close.queue`；所有业务队列挂死信参数指向 `inknexus.dlx.exchange` → `inknexus.dlx.queue`。多模块重复声明相同拓扑（比如 pay.success 队列 order 和 payment 都声明），参数完全一致，RabbitMQ 幂等声明。

## 四、句 4：Redis 缓存治理

> 简历原句：设计 Redis 缓存治理方案：使用空值标记防止缓存穿透，SETNX + Lua 实现互斥重建与原子释放，TTL 抖动降低缓存雪崩风险。

**面试官会盯的钩子**：三个问题各自的完整链路、解锁为什么必须 Lua、拿不到锁的线程在干什么、缓存一致性策略。

### Q4.1 穿透、击穿、雪崩分别是什么？你的方案分别是什么？

**参考回答**：**穿透**是查"根本不存在的数据"，缓存永远 miss，请求全打到 DB——常见于恶意用随机 ID 扫。我用**空值标记**：回源查不到时往缓存写 `__NULL__` 标记、TTL 只有 2 分钟（正常数据 30 分钟），2 分钟内同 ID 的攻击请求全部被缓存挡住。**击穿**是某个热点 key 过期瞬间，大量并发同时 miss、同时回源重建——我给重建加 **SETNX 互斥锁**，只放一个线程去查库，其他线程等缓存重建好直接读。**雪崩**是大量 key 同时到期（或 Redis 整体不可用），流量洪峰涌向 DB——前者我用 **TTL ±10% 抖动**打散到期时间，后者靠 Sentinel 对 `getBookById` 限流降级保护 DB（打优先级：DB 挂了是灾难，限流是可接受的降级）。

### Q4.2 互斥重建的完整流程讲一遍？拿不到锁的线程在干什么？

**参考回答**：流程六步：① 查缓存，命中直接返回；命中 `__NULL__` 返回 null；② miss 后 `SET lockKey = UUID EX 10 NX` 抢锁；③ 抢到后**双重检查**——排队期间可能别的线程刚重建完，直接返回避免重复回源；④ 回源 MySQL，查不到写空值标记（2 分钟），查到写 JSON（30 分钟 ±10% 抖动）；⑤ finally 里 Lua 校验锁值后删除；⑥ **没抢到锁的线程自旋等待**：每 50ms 醒来读一次缓存，最多 20 次（约 1 秒），期间重建者一旦写好它们立即命中返回；自旋耗尽（重建者卡死等异常情况）就**直接回源查库**保可用性——被打几下 DB 好过请求挂死，日志 warn 留证据。

有个追问可以预判："为什么自旋而不是返回旧值？"——因为我这是 miss 场景，**旧值不存在**（不是刷新场景），返回旧值无从谈起；自旋 + 超时回源是在"保护 DB"和"请求延迟"之间的折中，1 秒是可接受上限。

### Q4.3 为什么解锁必须用 Lua？锁的 value 为什么是 UUID？

**参考回答**：这是一个经典竞态：线程 A 持锁执行超过了锁的 10 秒 TTL，锁自动过期，线程 B 抢到锁开始重建；A 执行完直接 `DEL lockKey`——**删掉的是 B 的锁**，此时 C 又能抢锁，互斥被打破，DB 可能被多个线程同时打。解法是"删锁前校验锁是自己的"：SETNX 时 value 写 UUID 作为持有者标识，解锁时用 Lua 脚本：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

**GET 和 DEL 两条命令在 Lua 里原子执行**——如果分开两条 Redis 命令（先 GET 比对再 DEL），比对和删除之间锁仍可能过期易主，校验就白做了。这个方案我有单测：抢锁成功的线程才执行释放脚本、自旋的线程（未持锁）不释放。

### Q4.4 锁 10 秒过期了，业务还没执行完怎么办？没做续期吗？（⚠️ 诚实回答点）

**参考回答**：没做看门狗续期，这是我知道的边界。为什么可接受：临界区里只有**一条走索引的查询加一次缓存写入**，正常毫秒级完成，10 秒 TTL 留了两个数量级的余量；即使极端情况下锁过期、第二线程进入，代价只是多一次回源，**正确性不受影响**（写缓存是幂等的 set，不会写坏数据）——这是"锁失效退化成无锁"而不是"锁失效导致数据错误"的降级方向，可以接受。真要严格化，两条路：Redisson 的 watchdog 自动续期；或者像我一样评估临界区耗时后给出"TTL 远大于 P99 耗时"的论证。我选后者，因为引入 Redisson 换来的是对几乎不可能场景的保护。

### Q4.5 TTL 抖动怎么实现的？在哪一层做的？

**参考回答**：公式是 `ttl × (1 - 0.1 + random × 0.2)`，即均匀分布在 [0.9TTL, 1.1TTL]。实现分两处：**详情缓存**（手写 Cache-Aside）在 `BookDetailCache` 内部写缓存时抖动；**列表和分类缓存**（Spring Cache `@Cacheable`）我做了个 `JitterRedisCacheWriter`——实现 `RedisCacheWriter` 接口的**装饰器**，只在 put / putIfAbsent / store 写路径上对 TTL 抖动，读和删除原样委托给底层 `nonLockingRedisCacheWriter`，然后通过自定义 `RedisConfig` 把它注册进 `RedisCacheManager`，`books`（基准 30 分钟）和 `category`（基准 60 分钟）两个缓存全部生效。在 CacheWriter 层做的好处是**对业务代码零侵入**——业务侧 `@Cacheable` 该怎么写怎么写，抖动是基础设施行为。

### Q4.6 缓存和数据库的一致性怎么处理的？先更库还是先删缓存？要不要延迟双删？

**参考回答**：标准 Cache-Aside：**先更新数据库，再删除缓存**（图书详情精确驱逐该本，列表因分页内容会移位所以 `@CacheEvict(allEntries)` 全清）。为什么"删"而不是"更"缓存：并发写时两个线程的"更新缓存"乱序会让缓存永久停留旧值，删除后由下次读触发懒加载，天然收敛。为什么先库后删：反过来先删后写，删除到提交之间进来的读会把**旧库值**回填缓存。

延迟双删我也评估过：理论窗口是"读请求 miss → 回源读到旧值 → 此时写请求提交并删缓存 → 读请求把旧值写回"。但在我这里这个窗口被压缩了：详情重建本身在互斥锁内进行，写请求又是低频管理操作，且 30 分钟 TTL 兜底了最坏陈旧时间——图书详情对秒级陈旧不敏感，所以我**没有引入延迟双删的额外复杂度**，这是我基于业务容忍度的明确取舍，如果是对价格敏感的库存类缓存就不这么处理（库存我根本不走缓存，直接打条件更新）。

### Q4.7 Redis 挂了对系统什么影响？

**参考回答**：降级路径是"缓存失效、DB 直扛"：我的缓存代码里 Redis 异常不会让读请求失败，miss 就回源。但纯靠 DB 硬扛不够，所以 book 服务接了 **Sentinel**，`getBookById` 上有 `@SentinelResource` 限流，Redis 故障期间对读接口限流保 DB 不被打垮。这是"缓存层消失"场景下的完整预案。另外要区分：AI 会话记忆也在 Redis，挂了只是丢上下文（解析失败降级为空历史），不影响交易链路——**缓存和会话共用实例是我在生产化时会拆开的点**。

## 五、句 5：AI 客服与单元测试

> 简历原句：基于 LangChain4j + 通义千问实现 AI 客服 Agent，通过 Function Calling 提供图书/订单只读查询，Redis 保存会话记忆，SSE 实现流式响应；编写 81 个 JUnit 单元测试覆盖幂等、补偿等核心业务场景。

**面试官会盯的钩子**：Function Calling 原理、AI 怎么被约束不越权、SSE 细节、"81 个测试"的真实含金量。

### Q5.1 Function Calling 的原理？模型怎么决定调工具？

**参考回答**：我注册了两个 `@Tool` 类共 4 个工具：`searchBooks`（按书名搜索，默认 5 条、上限 10 条——限制工具结果体积防止撑爆上下文）、`listCategories`、`queryMyOrders`、`queryOrderDetail`。运行机制：LangChain4j 启动时把 @Tool 的**方法名、描述、参数描述**序列化成 JSON Schema，随每次请求发给模型；模型基于用户输入判断需要外部数据时，返回一个 tool call（函数名+参数 JSON）而不是文本；框架在本地反射执行该方法，把字符串结果作为 tool 执行消息回传，模型拿到结果再生成最终回答——一轮对话里可能多轮往返。所以工具的**描述质量直接决定模型选得准不准**，我每个工具的描述都写了"返回什么、给谁用"（比如订单工具明确写"当前登录用户的订单"）。

接入方式上：qwen-plus 走 DashScope 的 **OpenAI 兼容模式**（compatible-mode/v1），所以用 `langchain4j-open-ai` 就行，不需要专属 SDK——好处是以后换模型供应商只改 baseUrl 和 model 名。声明式接口是 `@AiService` 的 `BookAssistantAiService`，同一段 SystemMessage 和记忆，同时提供同步 `chat()` 和 `TokenStream chatStream()` 两个方法。

### Q5.2 怎么保证 AI 只读、且不会查到别的用户的订单？用户在对话里说"帮我查一下用户 123 的订单"呢？

**参考回答**：**靠架构约束，不靠提示词道德劝说**，一共三层。第一层，**工具层只读**：注册的两个 Feign Client 只有 `@GetMapping` 方法，工具类里物理上不存在能发起写操作的代码路径。第二层，也是回答你这个问题最关键的：**userId 根本不是模型的输入**——它不在 @Tool 参数里，不进 prompt，模型想伪造都没有入口。真实 userId 走的是和人类用户完全相同的权限链：网关注入 `X-User-Id` → `UserContextInterceptor` 存 ThreadLocal → Feign 拦截器写回下游请求头 → 订单服务做归属校验。所以模型就算被注入了"查用户 123 的订单"，`queryOrderDetail(123)` 到了订单服务也会被"非本人返回空"拦下，工具只会返回"没有找到该订单，或该订单不属于您"。第三层才是 System Prompt：明确"只查当前登录用户自己的订单、不编造数据、拒绝代用户下单支付"——这层负责体验引导，**安全语义全部在前两层强制**。所以我的答案是：prompt injection 对这个系统的最坏影响是模型说些废话，拿不到越权数据。

### Q5.3 会话记忆怎么存的？为什么自己实现 ChatMemoryStore？

**参考回答**：实现 LangChain4j 的 `ChatMemoryStore` 接口（getMessages / updateMessages / deleteMessages），落 Redis。几个设计点：**Key 是 `chat:memory:{userId}:{conversationId}`**，memoryId 由用户和会话双维度拼成，用户间隔离、同用户多会话隔离。**Value 存 String 不是 List/Hash**：整段消息序列化成 JSON 数组，每条只保留 `{type, text}` 两个字段——刻意不依赖 LangChain4j 内部消息类的序列化格式，升级框架版本时旧数据还能读，解析失败或遇到未知 type 就降级为空历史，不会拖垮对话。**TTL 2 小时**，每次写入刷新；窗口用 `MessageWindowChatMemory` 限制 20 条，超出丢最老的——防止长对话把 token 烧穿。选 Redis 而不是内存的原因：服务多实例部署时记忆要跨实例共享，且会话是天然可过期的临时数据，TTL 语义正好。

### Q5.4 SSE 流式怎么实现的？为什么用 SSE 不用 WebSocket？

**参考回答**：选型上，AI 回答是**服务器到客户端的单向推送**，SSE 足够：它就是长连接上的 `text/event-stream` 分块文本，比 WebSocket 轻——不需要协议升级、对 HTTP 基础设施（网关、nginx）友好、浏览器端 EventSource 自带断线重连。WebSocket 的双向能力在这里用不上。

实现细节：`SseEmitter` 超时设 120 秒（要大于模型最大回复耗时），`onTimeout` 里 complete。LangChain4j 侧 `TokenStream` 挂三个回调：`onPartialResponse` 每个 token 到达就推 `delta` 事件、`onCompleteResponse` 推 `done`、`onError` 打日志并 `completeWithError`。事件协议有三个：先推 **meta**（下发 conversationId，客户端后续带上来延续会话），中间 **delta**，结尾 **done**。两个边界处理：客户端中途断开时 `sendDelta` 写出抛 IOException，捕获后 `completeWithError` 停掉后续推送，不往死连接上写；另外浏览器原生 EventSource **只支持 GET**，而对话是 POST 带 body，所以前端用 fetch + ReadableStream 手动解析 SSE 流。同步 `POST /ai/chat` 保留为流式不可用时的降级备选。

### Q5.5 81 个测试具体覆盖了什么？不启动 Spring 的单测怎么测 MQ、幂这些东西？

**参考回答**：17 个测试类 81 个 `@Test`，全部是 Mockito 单测——`@ExtendWith(MockitoExtension.class)`，mock 掉 mapper / Feign / MQ publisher，只测被测类的**决策逻辑**。不启动容器恰恰是刻意的：秒级跑完全部用例，不需要任何中间件，可以挂在每次提交前跑。测试设计和简历那句话是一一对应的：

- **幂等**：eventId 已消费则 `verifyNoInteractions(stockMapper)`；PaySuccess 重投只发布一次库存确认（`thenReturn(1, 0)` 模拟两次消费）；重复支付请求只发一次支付成功事件；唯一索引冲突返回已有订单且补偿释放。
- **防超卖**：`deductStock` 返回 0 行断言抛 400 库存不足；`locked_stock` 不足确认失败；锁定为 0 时释放/确认幂等成功。
- **补偿**：取消、关单成功 verify 释放事件发布；下单失败 verify 补偿释放。
- **缓存**：抢锁成功重建并验证写入 TTL 落在 ±10% 抖动区间（ArgumentCaptor）、Lua 脚本释放锁；抢锁失败自旋读到重建值且**不**释放锁；自旋耗尽直接回源；空值标记命中不回源。
- **安全**：伪造 `X-User-Id` 头被网关覆盖、无 role 的旧 token 按 USER fail-closed、越权查他人订单返回 false。

MyBatis-Plus 的 Lambda 条件构造依赖实体元数据缓存，涉及它的测试在 `@BeforeAll` 里用 `TableInfoHelper.initTableInfo` 初始化，这是写 MP 单测的一个实操技巧。单测覆盖不到的是**真实中间件交互和并发竞态**——这些靠本地起全套环境手工验证 + JMeter 压测场景覆盖，集成测试是我列的改进项。

## 六、通用问题（开场/收尾必问）

### Q6.1 这个项目里你遇到的最难的问题是什么？（STAR，背熟）

**参考回答**（真实 bug 故事，最出彩）：**关单判定的"一秒之差"**。上线自测时发现偶发订单没被关掉：延迟消息明明到了，`closeExpiredOrder` 的 `expire_time <= now` 却判成"未到期"。排查发现是**时间精度问题**：Java 侧 `LocalDateTime.plusMinutes(30)` 带纳秒，而 MySQL DATETIME 只有秒精度，**四舍五入进位**——下单 10:00:00.7 存进去变 10:30:01；而延迟队列是从消息发送时刻起算 TTL 的，消息比数据库里存的过期时间**早约一秒**到达，此时 `now = 10:30:00.x < 10:30:01`，判定不成立，这一单就漏关了，只能等兜底扫描再关。修复是把 expireTime 写库前 `truncatedTo(ChronoUnit.SECONDS)`，让两个时钟对齐到同一精度。这件事给我的教训是：**跨系统边界传递时间，必须显式对齐精度和时区**，"看起来一样"的时间在不同存储里语义不同。后来我把这个案例写进了代码注释，防止后人改回去。

（备选故事：markPaid 幂等命中不能重发库存确认事件，否则二次确认会扣减**其他订单**的锁定库存——见 Q2.8。两个都可以讲，时间轴故事适合"印象最深"，这个适合"最有技术含量"。）

### Q6.2 有压测数据吗？QPS 多少？（⚠️ 高危问题，见防穿帮清单）

**参考回答**（诚实版）：我搭了完整的 JMeter 压测方案：图书列表冷/热缓存对比场景（50 并发，热缓存前 `FLUSHDB`）和下单写链路场景（20 并发，每个请求独立 clientRequestId 走真实幂等链路），压测报告模板里定义了 Avg/P95/P99 和错误率的采集口径。坦白说报告里的实测数字我还在整理，不想报一个没跑扎实的数——但**方案本身能验证的事情我可以讲**：比如幂等验证方法，用同一个 clientRequestId 并发提交 N 次，断言只产生 1 笔订单。

> ⚠️ 更好的做法：**面试前真把压测跑了，把数字填进报告**。jmx 和操作步骤都是现成的（benchmark/README.md）。有真实数字这条回答就变成加分项。

### Q6.3 流量涨 10 倍，你的系统先坏在哪？

**参考回答**：按顺序推演：**最先坏的是下单链路的 DB 写**——库存条件更新是单行热点，热门书所有请求挤一行，行锁排队 + 连接池耗尽，MySQL 先扛不住。第二步才是缓存读，Redis 单实例本身能扛十万级 QPS，不是第一瓶颈。所以优化路线：短期给**热点 SKU 做 Redis 预扣 + MQ 异步落库**（把 DB 行写从交易同步链路里摘出去）、MySQL 读写分离；中期按书的热度做**库存分段**；网关和各服务本身无状态，水平扩容即可。Feign 同步链路在 book 挂时会阻断下单，这个可以接受（没有价格快照本来就不该下单），但 stock 挂了是交易不可用，可以通过 stock 多实例 + 降级队列缓解。

### Q6.4 如果重做一次 / 下一步优化什么？

**参考回答**：按优先级：① **本地消息表（outbox）**替换"事务内直接发消息"，把生产端可靠性从"尽力而为 + 日志证据"升级为"保证投递"；② **JWT 缩短有效期 + refresh token / 登出黑名单**；③ 真实支付渠道对接，补齐支付失败回调与**退款补偿**；④ 前端逐条清购物车改成订单服务发"订单创建成功"事件、cart 消费后清勾选项（现在是前端成功回调里逐条删，失败的商品留在购物车里，能用但链路不优雅）；⑤ `t_mq_consumed_log` 加定期清理任务；⑥ 补集成测试（Testcontainers 起 MySQL/Redis/RabbitMQ）把竞态场景自动化。

### Q6.5 为什么消息队列选 RabbitMQ 不用 RocketMQ / Kafka？

**参考回答**：按需求匹配：我需要的是**延迟消息、死信、路由灵活、小消息量高可靠**——RabbitMQ 的 TTL+死信原生覆盖延迟需求，Kafka 没有延迟语义（要自己做时间轮）；RocketMQ 的延迟等级和事务消息很好，但我的延迟值需要可配置（30 分钟），TTL 队列方案更直接，且 Spring Cloud Alibaba 生态下 RabbitMQ 的 Spring AMQP 支持最成熟。Kafka 的强项是日志流和大吞吐，我的订单事件量级用不上。如果演进到需要事务消息（替代 outbox），那是迁移 RocketMQ 的合理时机。

## 附录：多层幂等白话版（先懂原理，再背话术）

三层幂等 = 三道防线，每道防一种**不同来源**的重复：

- **用户手抖**（双击按钮、超时重试）→ 下单唯一索引
- **并发双击**（两个请求几毫秒内同时到）→ 支付单 `uk_order_id` + 状态条件更新
- **MQ 重投**（业务做完还没 ACK 就宕机，Broker 重发，是 at-least-once 的正常行为不是故障）→ eventId 去重表

每层共同套路三步：**给操作一个唯一标识 → 让数据库判重（唯一索引 / 条件更新，不靠应用层 if）→ 重复了温和处理（返回原结果 / 跳过），不报错**。

### 第一层：下单唯一索引

前端在**打开下单弹窗时**生成 `clientRequestId`（不是点按钮时——同一次购买意图点多少次请求号都一样），订单表唯一索引 `(user_id, client_request_id)`。重复请求撞索引抛 `DuplicateKeyException`，后端查出**已有订单原样返回**，并补偿释放重复预占的库存。

- 为什么带 user_id：请求号只在用户维度唯一，跨用户撞号误伤，也防猜别人的请求号。
- 为什么不"先查再插"：两个请求同时查都说不存在 → 竞态。唯一索引是数据库保证的原子判重——**应用层检查都能被并发穿透，数据库约束不会**（三层共用的核心思想）。
- 细节：`client_request_id` 允许 NULL，MySQL 唯一索引对 NULL 不拦截，内部调用可以不带。

### 第二层：支付幂等 + 条件更新

两道机制：① `t_payment.order_id` 唯一索引，并发双击两事务同时 insert 必有一个回滚；② 已支付再请求直接返回，且**不重发 PaySuccess 消息**（重发会导致同一订单二次确认库存、扣掉**别的订单**的锁定库存）。

条件更新 = `UPDATE ... WHERE status = 上一个状态`，天然只成功一次：第一个把 0→1，后面全影响 0 行。0→1 支付、0→2 取消/关单、1→3 完成全是这个模式——延迟消息和定时兜底同时关单不冲突，靠的就是它：谁先更新成功谁赢，后到拿 0 行直接返回。

### 先懂 ACK：消息为什么会重投（第三层的前置知识）

RabbitMQ 递消息给消费者后**不马上删**，标记"未确认"，等消费者干完活主动回一句"处理好了"（ACK）才删。等不到这句 ACK——消费者处理到一半宕机，或 ACK 在网络里丢了——Broker 的唯一安全策略是**把同一条消息再发一遍**。因为 Broker 无法知道你死前做没做完，宁可重复也不丢，这叫 at-least-once（至少一次，可能多次）。所以**防重复的责任在消费端**，MQ 不帮你去重——这就是第三层存在的原因。

快递类比：Broker 是快递员，必须拿到你的**签收**才算送达；没签（你倒下了或签收单寄丢了），他会把**同一个包裹再送一次**。包裹上贴着唯一条码（eventId），你有个登记本（去重表）：每收件先按条码登记，登记成功才拆箱（干活）；发现条码已登过，说明这包裹之前送过、已处理，直接让快递员走。

事故现场时间线：① 订单服务发事件，事件体里写死 `eventId="aaa-111"`（重投多少次它都不变）→ ② 库存服务收到，插入去重记录、更新库存，正要回 ACK 时**宕机** → ③ Broker 等不到 ACK，重发同一条消息 → ④ 若消费者不设防就再更新一遍库存，账就错了 → ⑤ 设防后：第二次到达时 INSERT IGNORE 返回 0，跳过。

### 第三层：eventId 去重表

事件发布时生成 UUID 作为 eventId（重投不变），消费第一件事：

```sql
INSERT IGNORE INTO t_mq_consumed_log (message_id, consumer) VALUES (...)
```

返回 1 = 第一次消费，继续；返回 0 = 消费过，跳过。用 INSERT IGNORE 不用"先 SELECT"，还是防并发竞态（判重和占位合成一个原子操作）。

**最关键细节：去重 insert 和库存 UPDATE 在同一个 @Transactional。** 否则会出现"去重记了、业务没做成"：插入去重记录成功 → 库存 UPDATE 失败回滚 → ACK 失败消息重投 → 被去重表拦下 → **这次库存操作永远丢失**。同一事务后两者同生共死：业务失败记录一起回滚，重投可重试；业务成功记录保留，重投被跳过。两个方向都对。

### 一笔订单重复五次的时间线

| 时刻 | 发生了什么 | 谁接住 |
|---|---|---|
| t1 点下单 | 订单创建、库存预占 | — |
| t2 手抖再点 | 撞唯一索引 → 返回同一笔订单，多余预占释放 | 第一层 |
| t3 双击支付并发 | 一张支付单成功，另一张撞 uk_order_id 回滚 | 第二层 |
| t4 消费支付消息到一半宕机 | Broker 重投 | 重复来源 |
| t5 重投到达 | INSERT IGNORE 返回 0，跳过 | 第三层 |
| t6 假设 eventId 意外为空 | `WHERE status=0` 影响 0 行，无事发生 | 条件更新兜底 |

**面试一句话框架**："重复的来源有三种——用户手抖、并发双击、MQ 重投。每层我用'一个唯一标识 + 数据库唯一性裁决 + 温和处理'，区别只是标识不同：购买意图用 clientRequestId，支付单用 order_id，消息用 eventId。"

## 附录二：延迟关单与消息可靠性白话版

简历那句话是两件事拼起来的：**前半句**"TTL+死信+定时兜底"回答"30 分钟不付款怎么自动关单"；**后半句**"Confirm+重试+死信"回答"消息丢了失败了怎么办，为什么最后账是对的（最终一致）"。分开记。

### 一、为什么要关单

下单就预占库存（别人不能买）→ 如果永远没人关单，库存被占死。所以规则：30 分钟不付款自动取消订单、把预占库存放回去。

"30 分钟后做一件事"有四种做法：定时轮询（简单但延迟差、空扫浪费）、Redis 过期（过期事件不可靠、多一个一致性负担）、延迟插件（能力强但要装插件）、**TTL+死信（原生能力零插件）**。我的延迟值全局统一 30 分钟，所以选最简单的 TTL+死信。

### 二、TTL + 死信的机制：用"消息的死亡"当定时器

延迟队列**没有任何消费者、纯等待**，队列上配了 TTL=30 分钟和"死亡后转投地址"（死信交换机）。消息在里躺 30 分钟 → 过期"死亡" → RabbitMQ 不扔，按配置转投到**关单队列** → 真正的消费者在这里关单：

```
下单成功 ──发消息──▶ inknexus.order.close.delay.queue （TTL 30 分钟，纯等待）
                        │ 30 分钟后消息过期"死亡"
                        ▼
                 死信交换机 inknexus.order.close.exchange
                        │ 路由 order.close
                        ▼
                 inknexus.order.close.queue ← 消费者在这里
                        │ 条件更新 status 0→2（WHERE expire_time<=now）
                        │ 成功 → 发库存释放事件 → 库存服务放回预占
```

**队头阻塞**（必被追问）：RabbitMQ 只检查**队头**消息过没过期。如果消息各带各的 TTL，前面一条 10 分钟的会挡住后面 1 分钟到期的。我的过期时间全局统一，所以直接用**队列级 TTL**——所有消息同时间到、按序死亡，天然没这个问题。

### 三、定时扫描兜底 + 为什么两条路不打架

延迟消息的发送是**尽力而为**：下单链路里发送失败只 warn 不阻断（不能让 MQ 故障拖垮交易），这些订单没有延迟消息，靠每 2 分钟的定时任务扫 `status=0 AND expire_time<=now`（每批 500 条）关掉。

两条路**同时**触发同一笔订单也不会重复关：都走同一条条件更新 `UPDATE ... WHERE status=0`，谁先 0→2 谁赢，后到的拿 0 行直接跳过、也不再发释放事件——和幂等篇同一个思想：**数据库条件更新当裁判**。

### 四、生产端 Publisher Confirm（快递回执）

问题：消息发出去了，Broker 到底收没收到？发送方默认不知道——网络闪断时消息可能根本没到，库存就永远锁着没人释放。

Publisher Confirm = Broker 收到消息后给发送方**回执**（异步回调：ack/nack）；Returns = 消息到了 Broker 但路由不到任何队列（比如 routing key 配错）时**退回**给发送方。我的实现把回调挂到 RabbitTemplate 上，失败打 error 日志，CorrelationData 里放 eventId——日志能定位到具体订单。

诚实说法：**当前只留证据、不自动重发**，代码注释里写明了取舍——完整方案是本地消息表（outbox：业务和消息记录同库同事务落库，后台扫表重发），当前消息量 + 兜底机制下不引入这个复杂度。

### 五、消费端失败重试 + 死信

消费者处理失败（比如数据库瞬时抖动）不能把消息扔了：**本地重试 3 次**，间隔 1s→2s→4s 指数退避。3 次耗尽后**不回原队列**（`default-requeue-rejected: false`——回队列会立刻再消费，变成紧循环空转），而是走队列上配的死信参数，统一落进 `inknexus.dlx.queue` 等**人工介入**。JSON 坏掉的毒消息重试也没用，直接丢弃不重投（兜底扫描能补漏）。

### 六、为什么叫"最终一致"

跨服务没有大事务：订单改状态在 order 库，库存更新在 stock 库，中间**必然存在瞬间账对不上**（订单已支付、库存还没转正式，差几百毫秒）。最终一致的意思是：**不保证每一步同时成立，但保证最终一定收敛到正确状态**。收敛靠的是每步幂等 + 每条路有兜底：

事务内发消息（发送失败→事务回滚重来）→ Confirm 留证据（丢了能发现）→ 消费重试（扛瞬时故障）→ 死信（人兜底）→ 定时扫描（业务兜底）→ 条件更新（幂等裁判，重复了也没事）。

所以消息**重复**（eventId 去重 + 条件更新）、**丢失**（confirm 发现 + 扫描兜底）、**失败**（重试 + 死信）三种事故都有对策——这就是那句话的全部含义。

### 面试话术（三句话版）

> "订单 30 分钟不付款要自动关单释放库存。关单用的是 RabbitMQ 原生 TTL 加死信：延迟队列设 30 分钟队列级 TTL，消息到期死信转投到关单队列消费——统一过期时间用队列级 TTL，正好规避消息级 TTL 的队头阻塞；再加一个两分钟一次的定时扫描兜底消息发不出去的情况，两条路靠状态条件更新仲裁不会重复关单。可靠性上，生产端开 Publisher Confirm 留投递证据，消费端失败重试三次进死信队列人工兜底；跨服务没有强一致，但每步幂等加每条路有兜底，最终账一定是对的。"

## 附录三：项目里的"并发"到底在哪（被问"哪里用了并发"时答这个）

### 第一层：自己写的 JVM 并发点（4 处，都能指到代码）

1. **ThreadLocal 请求上下文**——AI 模块 `UserContextHolder`：拦截器 preHandle 把网关注入的 userId 写进 ThreadLocal，`afterCompletion` 里 `clear()`——因为 Tomcat 线程池复用线程，不清理会把上一个用户的身份串给下一个请求。同类的还有 common 里 `TraceIdFilter` 的 MDC（底层就是 ThreadLocalMap），finally 里 `MDC.remove()`。
2. **互斥 + 休眠自旋 + 双重检查**——`BookDetailCache.load()`：SETNX 抢锁失败的线程 `Thread.sleep(50ms)` 自旋最多 20 次等缓存重建，抢到锁后先双重检查再回源，最后 Lua 校验解锁。这是手写的并发协调模式。
3. **调度线程与消费线程的并发竞争**——`@EnableScheduling` + `OrderTimeoutTask`（每 2 分钟）和 MQ 关单消费者是**两拨线程并发地处理同一批订单**，靠数据库条件更新仲裁谁先 0→2。
4. **SSE 流式的跨线程交接**——`/ai/chat/stream`：请求线程拿到 TokenStream 就返回 SseEmitter，模型 token 到达后由 LangChain4j 的回调线程（HTTP 客户端 IO 线程）执行 `sendDelta` 推流——生产和消费数据的是**不同线程**，emitter 跨线程交接，断连靠回调里捕获 IOException 收尾。

### 第二层：用到的框架并发模型（不是自己写的，但面试可以讲认知）

- **Tomcat 线程池**：业务服务每请求一个工作线程——这正是 ThreadLocal 必须 clear 的原因。
- **网关 Netty 事件循环**：WebFlux 响应式非阻塞，少量 event-loop 线程扛全部网关流量，AuthGlobalFilter 里没有阻塞调用。
- **MQ 消费线程**：多实例部署时多消费者并发消费同一队列——这是消费端必须幂等的根源。

### 第三层（重头戏，主动把话题引过去）：分布式并发控制

被问"哪里用并发"，最有含金量的回答是：**这个项目的并发冲突不在 JVM 内，而在"多个实例同时操作同一行库存/同一笔订单"**。JVM 的锁管不了跨进程，所以正确性全部放在数据层裁决：

- 数据库**行锁 + 条件更新**防超卖、防状态机重复迁移；
- **Redis SETNX + Lua** 做分布式互斥（缓存重建）；
- **幂等消费**（唯一索引 / INSERT IGNORE 去重表）扛并发重复消息。

要诚实承认的：项目里**没有**线程池、@Async、CompletableFuture 的主动异步编排（JitterRedisCacheWriter 里的 CompletableFuture 只是实现 RedisCacheWriter 接口的原样委托）——这是选择不是遗漏：业务链路是同步短事务，自己开线程池反而把事务边界搅乱；真正需要异步的地方（支付结果、库存确认、延迟关单）用 MQ 做了事件驱动。

### ⚠️ 顺带发现的真实隐患：流式链路的 ThreadLocal 断点

`UserContextHolder` 是普通 ThreadLocal，写在 Tomcat 请求线程上；但 SSE 流式路径里 `TokenStream.start()` 之后，**工具（@Tool）的执行发生在 LangChain4j 的 HTTP 客户端 IO 线程上**，不是请求线程——那条线程上 ThreadLocal 是空的，`FeignAuthConfig` 拿不到 userId，Feign 调订单服务就不带 `X-User-Id`，订单接口 `@RequestHeader` 直接 400。

- 影响：**流式对话里问"我的订单"大概率失败**；同步 `/ai/chat` 没问题（工具就在请求线程上执行）；查图书的工具不受影响（book 接口不需要用户头）。
- 面试讲法：这是绝佳的"并发踩坑"素材——"跨线程交接时 ThreadLocal 会断，身份这类隐式上下文必须在切换边界显式传递"。修复方向：在请求线程把 userId 捕获进显式参数/上下文对象传给工具链，或为流式构建请求级作用域的工具实例；不建议用 InheritableThreadLocal（HTTP 客户端线程是池化的，继承时机不可控）。
